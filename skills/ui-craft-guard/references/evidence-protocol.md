# 审计证据协议 v0.2.1（兼容 v0.2.0 JSON）

目标：让 UI 判断可追踪、可反驳、可复查。此协议限制**结论的证据边界**，不把审美裁决自动化。

## 三个评价维度 × 四个问题层级

**评价维度（报告中必须分别作答）：**

- `visual_quality`（视觉质量）：层级、字体、比例、对齐、密度、颜色、组件与响应式表现；至少说明具体页面位置。
- `usability`（使用体验）：用户想完成什么任务、在哪里受阻、如何观察到错误或认知负担；不要把性能或 a11y 单独等同 UX。
- `design_identity`（设计个性与定位）：产品定位、目标受众、视觉意图及可识别性；允许“保留，不必改”，也允许“资料不足，暂不能断言”。

**问题层级（保留 v0.1.0 的分类）：** FLOOR / STRUCTURE / TASTE / POLISH。层级用于定位问题性质，不替代评价维度；例如键盘失焦是 `usability + FLOOR`，品牌中性色是 `design_identity + TASTE`。

## 四层审计覆盖（新增硬约束）

对每一层 `FLOOR`、`STRUCTURE`、`TASTE`、`POLISH` 均填写独立 `layer_coverage`，而不是只为有问题的层级写一行：

- `status=assessed`：提供至少一条可追溯的 `observed` 证据、检查范围与简短结论。**没有发现问题也可以是 assessed**。
- `status=not_assessed`：明确未检查的原因及限制；不得把“未检查”说成“无问题”。
- 每条发现所属的层级必须已被标记 `assessed`，否则不能对那个层级声称有经验证的结论。
- 四层覆盖不要求出现四条问题；不得为凑数量编造缺陷。

三个维度用于解释四层观察结果；不能把三个维度混成“UI 质量总分”，也不能用反模板命中数当作设计质量分。

## 发现编号与规则编号的可追溯关系

v0.2.1 JSON 要求每条 `findings[]` 分别填写：

- `finding_id`：本次发现的唯一标识，类似 `ISSUE-01`；不同发现可以引用同一规则。
- `rule_id`：原有 [设计规则库](design-principles.md) 中的真实 ID，例如 `G02`（设计与产品匹配）、`F02`（响应式与异常内容）、`I02`（状态反馈）。
- 如果问题来自特定项目、没有适配的规则库 ID，使用 `PROJECT:slug` 显式声明本地约束，不得捏造“标准规则”。
- `dimension` 是三维中的主要评价角度，`layer` 是四层中的问题分类，两者必须分别保存。
- 证据字段仍通过 `evidence_ids` 链接，不能用 `rule_id` 冒充证据。

旧版 v0.2.0 的 JSON 报告仍可由新版 `validate_report.py` 读取（使用旧字段 `id`，无 `layer_coverage`）；但**新报告须使用 `schema_version=0.2.1`**，以强制检查这两项兼容性修正。

## 最小证据记录

对每个证据记录唯一 `id`，并保留 `kind`、`status`、`locator`、`detail`：

| kind | 例子 | 可以支持 | 不足以支持 |
|---|---|---|---|
| `screenshot` | 路径、URL、视口、内容版本 | 可见层级、文字截断、局部视觉状态 | 点击功能是否真的成功 |
| `source_code` | 文件 + 行号/组件 + commit | 实现存在、条件分支、疑似问题 | 最终渲染及用户是否受阻 |
| `task_test` | 操作步骤、输入、预期与实际、环境 | 具体用户任务是否完成 | 总体用户研究结论 |
| `browser_run` | 路由、视口、环境、操作回执 | 渲染、焦点、状态与响应式现象 | 品牌偏好的真实来源 |
| `static_scan` | 检测器、版本、规则、匹配位置 | 需要复查的线索 | “已证实 AI 味”、WCAG 认证 |
| `brief` | 用户或产品负责人给的定位与要求 | 设计意图、限制条件 | 自动证明界面实现有效 |
| `brand_asset` | 已授权设计系统、Logo、色板、品牌指南 | 视觉语言的出处和约束 | 全部用户都喜欢的结论 |
| `user_research` | 真实访谈或可追溯任务记录 | 已观察到的用户需求/困惑 | 所有用户群体的普遍事实 |

`status=observed`：确实看过、执行过或读取过相关材料；给可复查定位和实测细节。`status=inferred`：由观察推出、尚未核实的推断；明确反例与待验证方法。`status=unavailable`：需要但当前拿不到；解释原因。不可将 `inferred` 或 `unavailable` 改写成真实测试结果。

## 决策门槛（重要）

发现问题的结论采用 `decision=change | retain | investigate`：

1. **change（建议调整）**：至少一条 `observed` 证据直接支持问题，并写出最小变更、影响、潜在副作用、复查方式；不能仅凭颜色/字体命中反模板清单。
2. **retain（保留）**：写出具体意图与支持证据。可保留简洁后台、渐变品牌页、特殊字体及反常规信息密度；保留不等于永不复查。
3. **investigate（待证）**：只有猜测、来源矛盾或缺少必要设计资料时，不能假装已经确定“应改”。
4. **design_identity + change**：必须有实际读取的 `brief` / `brand_asset` / `user_research` 证据，能说明当前设计怎样违背定位；缺失时降为 `investigate`。
5. **严重实测功能失效**：即使视觉精致也不能以审美为由标记 retain；至少建议修复或明确风险阻断原因。
6. **反证优先**：每条设计个性判断必须有反向解释、证据不足处及保留选项。审计者可得出“无需改”的结论。

## 工具能力等级（先声明，后审计）

- `full`：源码 + 实际浏览器页面 + 可复查任务测试；可做视觉、交互、布局的实测结论（仍不是自动用户研究）。
- `partial`：部分源码、设计稿或静态截图；可报告所见，用户流程结论需要标注未验证。
- `limited`：只有文字描述或不可访问页面；输出风险假设和所缺证据，禁止声称“已截图”“已通过”。

可选工具按**证明什么**使用：Playwright（操作与截图）、axe-core/Pa11y（部分 a11y 自动规则）、Lighthouse（性能等指标）、Storybook（组件状态）、design-extract（结构/Token 线索）。**没有装就不假装用过**。详细适用范围见 [tool-matrix.md](tool-matrix.md)。

## 严重度与验收

- `P0`：关键任务不能完成、数据/安全/严重可用性阻断。
- `P1`：主要目标明显受损、重复错误或范围很广。
- `P2`：可证实的局部摩擦、视觉层级或组件一致性问题。
- `P3`：情境相关的审美/微交互改进，接受不调整。

每条建议按 **判断 → 证据 → 最小调整 → 复查结果** 输出。审计阶段填写计划；只有真实执行后才填写已通过的复查。对照截图需同视口、同内容/数据状态、同主题和可解释的时间差异，保留失败记录。

## 程序可检查与不可检查的边界

仓库提供 `scripts/validate_report.py` 校验 JSON 审计记录结构、证据引用、决策前置条件、三维独立性、四层覆盖以及 `finding_id / rule_id` 的规则库映射。脚本无法验证截图是否真实、定位是否正确、任务是否确实失败、品牌策略是否优良；这些仍需要用户/审计者复核。规范示例位于 `examples/audit-cases/`。
