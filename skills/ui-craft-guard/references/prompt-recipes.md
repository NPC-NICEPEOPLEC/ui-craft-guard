# UI Craft Guard 使用话术手册

> 本文件只提供**供用户复制的任务话术**，不是新的 Agent 执行规范。遇到冲突，以 [SKILL.md](../SKILL.md) 为执行准则；规则编号看 [Rulebook](design-principles.md)，证据和决定门槛看 [evidence-protocol.md](evidence-protocol.md)。不要在这里复制另一份完整规则书。
>
> **推荐方式**：第一次审计只用阶段 ①；读完报告后再进入 ②；确定范围之后才授权 ③；实际改动之后才进行 ④。阶段是用户操作流程，不是新的 Skill 模式。依照需要，也可以独立使用下面的专项话术。

## 场景入口：我该用哪一条？

| 你的情况 | 直接复制 |
|---|---|
| 网站做到一半，不知道问题在哪 | **① 自主诊断** |
| 已有审计报告，但不知先改什么 | **② 根因与设计决策** |
| 已确认方案，准备真正修改代码 | **③ 执行改进** |
| 页面改过了，需要防止越改越差 | **④ 批判性对比** |
| 只看某一个页面 | 下方 **单页聚焦** |
| 正在设计全新页面 | 下方 **从零构建** |
| 中文内容为主的站点 | 下方 **中文长内容专项** |
| 上线前避免严重缺陷 | 下方 **上线前检查** |

## ① 自主诊断｜不知道哪里有问题时（audit）

```text
请加载 ui-craft-guard，使用 audit 模式对当前网站做一次自主诊断。

背景：网站正在开发，我无法准确指出有哪些设计或交互问题。
请先主动了解代码、页面、现有设计系统、品牌资料、目标用户和核心任务；
不要让我先指定缺陷，也不要直接开始美化。

具备浏览器与运行权限时，请实际打开关键页面，覆盖代表性桌面和移动视口，
重放能影响用户主要任务的流程；没有能力则明确标记 partial/limited 和未测项。
如果是多页面网站，先给出页面清单，按用户任务的重要性选代表性路径，
说明抽样范围，不要把少量页面说成已经检查整个网站。

先检查 FLOOR、STRUCTURE、TASTE、POLISH 四层并记录 assessed/not_assessed
及证据范围，允许“已检查但未发现问题”，不要求四层都有缺陷。
再独立评价 visual_quality、usability、design_identity，不做 UI 总分。

针对每项重要发现，给 finding_id、实际 rule_id（或 PROJECT:slug）、
Evidence IDs、具体位置、影响、最强合理反证、可能的共同根因、
change/retain/investigate、P0–P3 优先级和验证方法。
检查哪些合理设计值得保留；来源不足时不擅自否定品牌选择。
静态扫描是线索，不能当作视觉或任务测试已经完成。

输出：审计范围与能力边界、四层覆盖表、三维评价、证据与问题清单、
保留清单、值得优先处理的最多三个根因（如不足三个则如实列出）、
以及仍需验证的假设。

本轮只审计，不得修改代码、样式、配置或文件；不要伪造截图或通过记录。
```

## ② 根因与设计决策｜审计后、修改前（仍为 audit 的分析阶段）

```text
继续使用 ui-craft-guard 的已确认审计结果，进入“根因与设计决策”阶段。
这是 audit 后续的分析，不是新增一个 Skill 模式。本轮不修改文件。

请以已有 finding_id、rule_id、Evidence IDs 和当前设计意图为输入；
先核对每项结论是否有足够证据，遇到证据缺失或反证成立时修正判断。
把问题按“局部缺陷 / 共享组件或 Design Tokens / 信息架构与任务流程 /
品牌定位未知、应先调查”分组；识别是否多个症状来自同一根因。

按用户任务影响、问题范围、回归风险、实施成本与可验证收益排序，
不要仅凭审美喜好或问题数量排序。已有效的功能和设计列入保护清单。

对真正存在重要取舍的地方，给出 2–3 个具有不同结构或设计意图的方案，
分析预期收益、牺牲、证据缺口与撤回条件；不必为每个小问题凑三个方案。
最终推荐一条可分批实施的路径，列出每批的验收标准与待审批范围。
即使建议保留原设计，也解释证据和适用条件。

输出：根因映射、推荐方案及反对意见、保留与待证事项、
最小修改范围、实施顺序、验收条件。本轮不修改任何代码。
```

## ③ 执行改进｜已确认要修改什么时（redesign）

```text
请加载 ui-craft-guard，进入 redesign 模式。
我授权实施上一轮**已确定范围**的 UI 改进，未确认的项目不擅自扩大范围。

先核对审计报告和批准的设计决策，再分批修复。
优先保证 FLOOR 及关键业务操作，不为更美观破坏品牌、可访问性、
数据、路由或已有功能。共性问题优先在正确的共享组件/设计 token 层修复；
局部问题采用最小变更，保留代码 diff 和原设计合理选择。

每次改动绑定 finding_id、rule_id 和对应修改文件。
具备浏览器时用同内容、同主题、同视口、同状态的前后截图，
重放相关任务并检查桌面/手机、中文长文案、键盘焦点及异常状态；
不可执行的检查如实标记未运行，不用“构建成功”代替 UX 改善。

输出：实际改动与差异、问题 ID 到代码位置的对应、
已通过/失败/未执行的检查、退化风险、剩余问题。
不为完成指标而修改被明确 retain 的设计。
```

## ④ 批判性对比｜确认修改是否值得（compare）

```text
请加载 ui-craft-guard，使用 compare 模式批判性比较旧版与新版。
不要预设新版本更好，也不要因为它是本次修改就为结果辩护。

读取先前审计与批准方案、真实前后版本、代码 diff 和已有测试证据；
在能访问页面时使用相同内容、视口、主题和任务状态重新验证。
逐层核对 FLOOR/STRUCTURE/TASTE/POLISH 覆盖，独立审视
visual_quality、usability、design_identity。

按发现 ID 说明：已改善 / 持平 / 退化 / 尚未验证；
关注新引入的功能故障、阅读困难、移动端问题和品牌表达偏离。
主动寻找支持旧版本的最强反证，不把“更简洁”自动等于“更好”。

若仍由同一个 Agent 执行，请明确这是“批判性自我复查”，
**不是独立红队验收**；真正独立评审应由另一 Agent/独立会话在不预设结论下复核。
最后报告经过实际测试的结果、尚未验证的事项、应保留/修正/撤回的改动，
并对照本轮验收标准说明是否达成，而不是给一个无依据的总分。
```

## 专项话术：无需完整四阶段时

### 单页聚焦（audit）

```text
请使用 ui-craft-guard 的 audit 模式仅检查当前页面，不要扩大到全站。
按四层记录已检查/未检查，三维独立评价，重点找出影响页面主任务的
少数几个问题。绑定 finding_id、rule_id、证据与反证；说清哪些不必改。
本轮不修改文件。页面之外只记录依赖和潜在风险，不宣称已检查。
```

### 多页面一致性与设计系统（audit → redesign）

```text
请先以 ui-craft-guard 的 audit 模式抽样检查网站主要页面的
字体、间距、色彩角色、组件状态和 Design Tokens；区分真实品牌例外
与无意的不一致，识别共享根因和受影响页面。先给证据与推荐方案，
不立即改代码；待我明确授权后，才用 redesign 修改共享规则并回归。
```

### 从零构建页面（build）

```text
请使用 ui-craft-guard 的 build 模式，为当前需求设计新页面。
先确认目标用户、主任务、内容优先级、品牌来源和不可改变的行为。
在确有重要取舍时提供 2–3 个真正不同的结构/视觉方向及代价，
而非仅更换配色；采用明确的设计 Tokens，完成状态和响应式处理。
实际可验证时复查四层风险，并独立评价视觉质量、使用体验和设计个性。
不要使用虚构用户评价、业务指标或未经授权的素材。
```

### 中文长内容专项（audit 或 redesign）

```text
请使用 ui-craft-guard 检查当前中文内容页面的真实阅读任务：
标题断行、行高、字重、标点、中英文与数字混排、字体回退、
长链接、手机小视口及放大后可读性。先给证据、例外和应保留的节奏；
仅在我明确要求修改时进入 redesign。不要把固定字符数当成统一规范，
也不要为了“高级感”自动添加无意义的英文眉标。
```

### 上线前风险扫描（audit）

```text
请使用 ui-craft-guard 做上线前的 UI 风险检查。
优先检查 FLOOR 的关键任务、表单/状态/键盘与信息可读性，
再覆盖 STRUCTURE/TASTE/POLISH 及三个独立评价维度。
实际重放最关键路径，标出 P0/P1 阻断项、对应证据、未测试环境与回归风险；
没有测试权限时不能说“上线通过”，只给可执行的补验计划。
本轮不修改文件。
```

## 使用与证据边界

- 短话术和完整话术都是入口；**规则和权威流程不由本文件定义**，详见 [SKILL.md](../SKILL.md)。
- `audit` 不改文件；阶段 ② 不创造第五模式；阶段 ③ 的指令是实施授权，未批准的范围不扩大；`compare` 不自动构成独立红队。
- 真实浏览器和代码权限决定能证明什么；扫描器、静态截图及合成 JSON 只支持其对应证据范围。
- 结构化输出可使用 [AUDIT_REPORT](../templates/AUDIT_REPORT.md) 与 [DESIGN_DECISIONS](../templates/DESIGN_DECISIONS.md)；机器可读 JSON 的 `schema_version=0.2.1` **是独立于 Skill 版本的报告契约**，不因 Skill 文档小改版而自动上调。
- 可复现的原创教学示例见 [workflow-walkthrough](../../../examples/workflow-walkthrough.md)，不能把它说成对真实客户网站完成的盲测。
